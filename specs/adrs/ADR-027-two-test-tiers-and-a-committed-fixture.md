# ADR-027: Two Test Tiers, and a Committed Fixture for the Upper One

**Status:** approved  
**Date:** 2026-08-28

## Context

This CLI's entire job is invoking `bd` and `git` correctly, so a test
suite that fakes both tests almost nothing that matters: every trap it
exists to guard is a property of the real tools. Its exit status is part
of its contract ([[frd-swarm-core]], AC-SWARM-CORE-001.1), and a status is
not observable from inside the process that would return it.

Against that, the tests must run on macOS, Linux and Windows
([[adr-023]]), and the tracker is a heavier dependency than git.

This repository already has the machinery for the upper tier. Cases under
`cli/testdata/cases/` are pure data — a `case.toml` naming the argv and
the expected exit status, an `input/` corpus, and committed `expected/`
artifacts — replayed by one harness, and replayed a second time from a
CRLF working tree so a line-ending difference is caught rather than
assumed away.

What those cases have never needed is a *stateful* fixture. A spec-CLI
case is a directory of markdown. A swarm case needs a git repository with
a branch and commits, a tracker holding a run epic, a phase chain, a flat
target and beads beneath it, and sometimes worktrees. Two ways to get one
exist: generate it with code, or commit it and restore it.

## Decision

We will test in two tiers.

**Unit** — components are exercised against a fake process runner that
replays recorded tool output. Because a command builds a plan value
([[adr-024]]), the plan itself is asserted without running anything, and
each decoder is tested against the recorded shapes it must accept.

**End-to-end** — the compiled `swarm` binary is executed as a subprocess
against a fixture **restored from committed artifacts**: a `git bundle`
holding the repository, and a tracker export the case imports. Each case
materializes its own copy into a temporary directory, runs there, and
deletes it; nothing is rolled back and no case shares state with another.
Output and exit status are compared against committed snapshots through a
declared normalization list.

The CLI ships no fixture-generating command.

**On Windows, cases run against the CGO-free, server-mode `bd` install.**
It needs no MinGW-w64 toolchain on the runner, and it matches the
CGO-free stance of our own build. The cost is that Windows then exercises
a different tracker topology from Linux — a Dolt server on a loopback
endpoint rather than an embedded database — so a Windows-only failure is
not immediately attributable to the platform rather than to the mode. We
accept that for the first leg; the remedy, if attribution becomes the
problem, is adding the CGO toolchain to the runner rather than changing
anything here. Whether that install needs a server started before a case
can restore its fixture is unmeasured, and the fixture harness is where
it will be handled.

## Alternatives Considered

| Option | Pros | Cons | Why rejected |
|--------|------|------|--------------|
| Unit tests only, everything faked | Fast; runs anywhere | Every trap the CLI exists to guard is a property of the real tools, so the suite would pass while the thing it guards is broken | Tests the wrapper and not the wrapping |
| End-to-end only, real tools throughout | Highest fidelity | A decoder's handling of a rare empty shape is nearly impossible to provoke through the real tool | Cannot reach the cases that matter most |
| In-process invocation of the command tree | Fast; no build step; the existing spec-CLI harness does this | Cannot observe a real exit status, which is a first-class part of this CLI's contract; shares the test process's working directory and environment, so a command that mishandles either passes | Cannot test the contract's most-routed-on property |
| Recorded tool output as the only fidelity | Deterministic; no tool needed at test time | A recording rots silently when the tool changes, which is exactly the failure class this CLI exists to catch — the corpus has four retracted claims about tool behaviour to prove it | Reproduces the failure being fixed, one layer down |
| A `swarm scaffold` command generating the fixture | One command a human can also run by hand; the fixture tracks the code that builds it | Ships a development affordance in the production binary; the generator is code that can be wrong, and a case passing against a fixture that does not resemble a real run is a false pass nothing catches; generated commits carry fresh shas, so every snapshot needs sha normalization | Puts a large body of environment-setup code inside the tool, and buys nondeterminism with it |
| A fixture repository as a git submodule | The fixture is real, and grows without code | Submodules complicate every clone and every CI checkout, and a fixture change is a two-repository change with a pointer bump between them — for a fixture measured in kilobytes | Ceremony out of proportion to the artifact |
| Committed `git bundle` plus a tracker export | The fixture is a real repository with fixed commit shas, so snapshots need no sha normalization; a fixture change is reviewable as a diff; no generator to be wrong; no development command in the binary | Two artifacts to keep in step with the manifest key set; the tracker half restores through an import rather than being byte-restored | N/A — selected |
| Roll the fixture back after each run | One materialization for the whole suite | A failed or interrupted case leaves the fixture dirty and poisons the next; cases cannot run in parallel; the rollback is itself a mutation performed when the state is not what was expected — the thing [[adr-026]] declines to do elsewhere | Order-dependent, and it makes one case's failure into the next case's failure |

## Consequences

**Positive:**

- The exit status, the printed invocations and the stream separation are
  tested as a caller sees them, because a subprocess is what a caller
  runs.
- Commit shas in the fixture are fixed, which removes the largest source
  of snapshot churn. Measured here: `git bundle create` followed by two
  clones produced the same head sha in both, from a 530-byte bundle for a
  one-commit repository.
- There is no fixture generator, so there is no generator to be wrong,
  and no code path whose only consumer is the test suite.
- Copy-per-case gives every case a clean world it cannot lose, and makes
  the suite parallelizable without any further work.
- A fixture change is a reviewable diff — a new bead, a different phase
  chain — rather than an edit to code that produces one.
- A tracker upgrade that changes a subcommand's shape fails this tier,
  which is the guard the recorded tier cannot provide.
- Rare shapes are reachable in the unit tier, where the real tool cannot
  easily be made to produce them.

**Negative:**

- The fixture and the declared manifest key set must change together. A
  key added without re-recording the core fixture leaves cases asserting
  a manifest shape the code no longer writes; the version stamp is what
  makes that detectable rather than a thing to notice.
- Three kinds of fixture is a distinction somebody must apply correctly.
  Re-recording a legacy fixture to make it pass is a one-line change that
  silently removes a guarantee, and only the version stamp and a reviewer
  stand in its way.
- The tracker half restores through the tracker's own import rather than
  being copied byte for byte. The import preserves the export's own
  `created_at` and `updated_at`, so the fixture's tracker timestamps are
  as fixed as the git shas and neither needs normalizing. What does need
  it is what the surface measures rather than what the fixture holds —
  step durations and stream digests, which differ on every run.
- Snapshot normalization remains a standing hazard in both directions:
  too little and every case fails, too much and the case stops asserting
  what it was written for. The substitution list is declared per case and
  is itself something to review.
- A human debugging by hand restores the fixture with the same two
  commands a case runs, rather than with one command the CLI provides.
- Cases needing the tracker do not run everywhere. `bd` documents a
  Windows install, but its CGO-free install is server-mode rather than
  embedded, so the tracker a Windows case would run against is not the
  one a Linux case runs against; the platform guarantee for those
  commands rests on the unit tier plus the cross-compile until a Windows
  leg is actually run.

## How the fixture evolves

A committed fixture is a frozen world, and the code around it moves. Three
kinds of fixture, distinguished by what they are for rather than by when
they were made, keep that from becoming a slow corruption:

- **The core fixture** is the canonical run: one repository, one run epic,
  a phase chain, a flat target, beads beneath it. It tracks the current
  code and is re-recorded whenever the shape it asserts changes.
- **A variant** is a world the core does not express — a conflicted merge,
  a resumed run, a second target, a run whose front is empty. It is
  **derived from the core as a branch** rather than authored beside it, so
  a change to the core reaches it. A `git bundle` carries every ref, so a
  variant is a branch in the same bundle and shares the core's objects and
  its shas.
- **A legacy fixture** is deliberately frozen at a shape an older version
  wrote, and exists solely to prove the current code still reads it. It is
  never re-recorded. Re-recording one destroys the only evidence that
  reading an older shape works, which is the failure this kind exists to
  prevent — and it is the tempting fix when it goes red.

**Every fixture records the contract version it was recorded against.**
That one stamp is what makes the three kinds mechanically distinguishable
rather than a matter of everyone remembering: the core's stamp must equal
the current version of [[contract-swarm-json]], and a legacy fixture's
must be older than it. A core fixture whose stamp has fallen behind is a
re-record that was missed; a legacy fixture whose stamp has caught up is
a legacy fixture somebody re-recorded.

**Backward compatibility becomes testable rather than asserted.** The CLI
will read manifests written before it existed — the sprint skills write
them today — and will keep reading manifests written by earlier versions
of itself. A legacy fixture per shape worth supporting turns that from a
claim into a case, and the shapes not worth supporting are the ones with
no legacy fixture, which is a decision visible in the tree.

None of this is built now: there is one fixture and one shape. It is
decided now because the alternative is discovering it at the moment a
second shape is needed, when the cheap thing to do is copy the core
fixture and edit it, and the cheap thing is what makes a variant drift.

## The larger fixture this does not build

The evaluation suite for the `bead-bonanza` skill itself — target epics,
stray beads, work orders that instruct an agent to build something, and
an assessment of what the run produced — is a different artifact with a
different lifecycle, and it belongs in a repository of its own rather
than in this one's `testdata`. This decision covers the fixtures that
prove one command behaves; it deliberately does not attempt the fixtures
that prove a whole run behaves, and nothing here forecloses that
repository.
