# agent-plugins-j7f — [bug] generate-schemas.sh silently destroys the schema when run with strata older than the inheritance fix

## Full bead description

scripts/generate-schemas.sh has no version floor for strata. Run it with
strata-cli 0.7.0 as installed by .claude/hooks/session-start.sh and it
regenerates cli/core/schema/spec-model.schema.json with EVERY inherited
envelope property dropped:

```
"Adr": { "additionalProperties": false, "properties": {} }
```

All twelve document types lose title, description, slug, type, status,
updated_at and their required entries — the file goes from 2202 lines to
1326. The script reports success. Committing that would silently disable
frontmatter/missing-property and frontmatter/schema for every document type,
i.e. destroy the checks this repo's CI now depends on.

Root cause is upstream and already FIXED there: strata-lang/strata commit
8997153 'Fix: allowAdditionalProperties: false silently dropped struct
inheritance (#289)'. Our schemas use 'struct Adr: DocumentFrontmatter {}'
together with additionalProperties: false, which is exactly the combination
that regressed. The binary the session-start hook installs predates the fix;
building from the strata checkout at HEAD produces output byte-identical to
what is committed.

Discovered 2026-08-05 while adding a FindingDetail variant for agent-
plugins-5xo: the regeneration required for that change would have shipped
the destroyed schema had the diff not been reviewed. What saved it was
reading the diff, not any gate.

Fix options, roughly in order of value:

1. Version floor in generate-schemas.sh — refuse to run below the
first strata release containing 8997153, naming the commit.
2. A post-generation sanity assertion: every document-type definition
must carry a non-empty required list. Cheap, and catches any future
regression of this shape rather than this one version.
3. Pin the strata version the session-start hook installs.
4. Wire generate-schemas.sh --check into CI. The checks.yml comment
already explains why it is not there (needs a Rust toolchain);
option 2 removes most of the need.

### Steps to Reproduce

1. Ensure the strata on PATH predates strata-lang/strata commit 8997153
("Fix: allowAdditionalProperties: false silently dropped struct
inheritance (#289)") — strata-cli 0.7.0, the version
.claude/hooks/session-start.sh installs, is such a build.
Check with strata --version.
2. From the repository root, run scripts/generate-schemas.sh.
3. Observe that the script reports success and exits zero.
4. Inspect the regenerated cli/core/schema/spec-model.schema.json.

**Expected:** the regenerated file is byte-identical to the committed one
(2202 lines), and every document-type definition retains its inherited
envelope properties (title, description, slug, type, status,
updated_at) and its required list. Building strata from a checkout at
HEAD and re-running produces exactly this.

**Actual:** the file is 1326 lines. All twelve document types lose every
inherited envelope property and their required entries, e.g.
"Adr": { "additionalProperties": false, "properties": {} }. The script
still reports success, so nothing signals the loss.

**Where it manifests:** scripts/generate-schemas.sh (no version floor) →
cli/core/schema/spec-model.schema.json → the Schema Registry component,
which silently stops enforcing frontmatter/missing-property and
frontmatter/schema for every document type.

### Notes / Decision

Prerequisite for the reference-integrity feature: work order agent-plugins-
9kb.1 (delta MODEL) regenerates all three Strata sources and is blocked on
this. Committing a schema regenerated by an older strata would silently
disable the frontmatter checks CI depends on.

**## DECISION (2026-08-07)**

All four options in the description were put to the user. Selected: 2 + 3.

1. Version floor naming 8997153 — NOT selected. Dominated by option 2: it
guards only the too-old case and would NOT have caught what actually
happened this session, since HEAD (ce18d66) is far above any such floor and
still produced wrong output. Version strings cannot discriminate here —
44c1955 (destroys the schema) and 840f9ba (correct) both report strata-cli
0.7.0.
2. Post-generation sanity assertion: every document-type definition must
carry a non-empty required list — SELECTED. This is the actual guard and
satisfies this bead's acceptance criterion verbatim. Version-independent,
so it catches this SHAPE of regression rather than one known-bad build.
3. Pin the strata the session-start hook installs — SELECTED, with an
adjustment. The user has since decided to adopt strata HEAD (agent-plugins-
tix, wired to block this bead). So "pin" does NOT mean pinning to 840f9ba.
It means making provisioning verifiably correct: the hook builds from the
checkout and stamps the built commit in ~/.cache/strata-cli/built-commit,
and a stale stamp must not be able to leave an older binary installed while
reporting success.
4. Wire generate-schemas.sh --check into CI — NOT selected. Needs a Rust
toolchain, the documented reason it is absent from checks.yml, and option 2
removes most of the need. CI-gate expansion is agent-plugins-9ko.

Ordering: agent-plugins-tix adopts HEAD and regenerates. This bead adds the
guard that makes a future bad regeneration fail loudly. Do not redo tix's
work here.

### Acceptance Criteria

generate-schemas.sh fails loudly rather than emitting a schema whose
document types have no properties, when run with a strata that drops struct
inheritance.

## Retro

### Approach taken

Implemented both selected options.

**Option 2 (primary guard).** Added a step ("2.5") to `scripts/generate-
schemas.sh`, right after the bundled JSON Schema is built and before it (or
any other output) is synced into the tree. It shells a small inline
`python3` script (no external deps — `json` + `sys` stdlib only, consistent
with `scripts/validate-corpus.py`'s existing use of python3 in this repo)
against the freshly generated `spec-model.schema.json`. The script:

1. Reads `definitions.DocumentType.enum` — the kebab-case list of document
   type values (`"adr"`, `"system-blueprint"`, …).
2. Converts each value to the PascalCase struct name convention this repo's
   schemas use (`"system-blueprint"` → `SystemBlueprint`) to get the list of
   document-type definitions to check.
3. Asserts each such definition exists in `definitions` and has a non-empty
   `required` array. Missing definitions and empty/missing `required` lists
   are both reported (all offenders at once, not just the first), and the
   script exits 1 with a message pointing at the upstream commit, the fact
   that `strata --version` can't discriminate a good build from a bad one,
   and where to check the actual provenance
   (`~/.cache/strata-cli/built-commit`).

**Option 3 (provisioning correctness).** Edited `.claude/hooks/session-
start.sh`'s strata-provisioning block. Added a `_fetch_unverified` flag,
set only when the `git fetch` + `git merge --ff-only` step against
upstream explicitly fails (not when the checkout is deliberately built
as-is because it's on a non-default branch or has uncommitted changes —
those are intentional, already self-explanatory in their own log lines,
and not a freshness gap). When the installed binary's stamp matches the
local HEAD *and* that fetch failed, the hook now emits a `WARNING:` line
explaining that the stamp match only proves the binary matches disk, not
that disk is caught up with upstream, instead of the plain "strata CLI
current" success line it printed before. This directly targets "a stale
stamp must not be able to leave an older binary installed while the hook
reports success" without pinning to an old commit and without needing an
actual network failure to reproduce (the branch is structurally new code —
verified with `bash -n` and by reading the modified control flow; the
failure-injection this guards against needs a real fetch failure against
github.com, which is out of scope to fabricate for this bead per the
explicit "Do NOT rebuild strata. Do NOT touch the /home/user/strata
checkout" instruction — this session's strata build is HEAD (ce18d66)
already, per the environmental facts).

### Observed pre-fix failure (RED before GREEN)

Could not cheaply reproduce a real strata-44c1955 build (needs a ~90s
cargo build against a different checkout per the environmental facts, and
the instructions explicitly say not to do this). Instead, synthesized the
exact corruption shape strata 44c1955 is documented to produce, applied it
to a copy of the real generated schema, and ran the assertion logic
against it directly:

```
python3 -c "
import json, copy
d = json.load(open('cli/core/schema/spec-model.schema.json'))
bad = copy.deepcopy(d)
bad['definitions']['Adr'] = {'additionalProperties': False, 'properties': {}}
json.dump(bad, open('/tmp/bad-schema.json','w'))
"
```

Running the assertion against `/tmp/bad-schema.json`:

```
error: generated schema has document type(s) with an empty or missing 'required' list: Adr
exit=1
```

**This is the rejection** — the guard fires and names the offending type,
exactly as the acceptance criterion requires ("fails loudly ... rather
than emitting a schema whose document types have no properties").

Running the same assertion against the real, correct, committed schema
(copied unmodified):

```
ok - all document types have non-empty required lists
exit=0
```

Then, separately, ran the actual `strata build` toolchain (this session's
HEAD build, ce18d66, which contains the upstream fix) via
`scripts/generate-schemas.sh` for real — the assertion ran silently (no
error) as part of that regeneration, and `scripts/generate-schemas.sh
--check` reported "generated artifacts are up to date" afterward, confirming
the guard doesn't produce false positives against a correct build.

### Implicit decisions and why

- **Where in the script:** placed the assertion immediately after step 2
  (the bundled JSON Schema is written to `$WORK/schema/spec-model.schema.json`)
  and before step 3 onward, so a corrupted bundle is caught before the specs-
  config overlay schema, the Go embed wrapper, the Go structs, or the
  Markdown reference are generated from (or alongside) it, and — critically —
  before `sync_dir` ever copies anything into the tracked tree. Nothing
  downstream of the corruption point runs before the check fires.
- **How to parse the schema:** a dependency-free inline `python3` heredoc
  (stdlib `json` only), matching the instruction to prefer a dependency-free
  approach and the existing precedent of `scripts/validate-corpus.py` using
  python3 in this repo (that script additionally needs `jsonschema`/`pyyaml`
  for its fuller job; this check needs neither).
- **How to identify "document type" definitions without hardcoding names:**
  derived the list from the generated schema's own `definitions.DocumentType`
  enum rather than a hardcoded name list or a second read of
  `schemas/vocabulary.strata`. This keeps the check honest against schema
  evolution (a renamed or newly added document type is picked up
  automatically) while staying self-contained to the one generated artifact
  the script already has in hand. It relies on this repo's existing naming
  convention (struct name = PascalCase of the enum's kebab-case value, e.g.
  `system-blueprint` → `SystemBlueprint`), which held for all 11 current
  document types when checked against `cli/core/schema/spec-model.schema.json`.
  Chose this over hardcoding partly because the enum itself is structurally
  immune to the bug being guarded against: it's a plain string enum with no
  struct inheritance, so it can't be corrupted the same way and remains a
  trustworthy anchor even in the exact scenario this check exists to catch.
- **Failure message phrasing:** named the upstream commit and PR
  (8997153, "Fix: allowAdditionalProperties: false silently dropped struct
  inheritance (#289)"), explained why `strata --version` can't be used to
  diagnose it, and pointed at `~/.cache/strata-cli/built-commit` as the
  actual provenance signal — mirroring the diagnostic path a future agent
  hitting this would need, based on how this bead itself was diagnosed.
- **Bead says "twelve document types"; only 11 struct definitions inherit
  `DocumentFrontmatter`** in the current schema (`Adr`, `Frd`, `Contract`,
  `Standards`, `SystemBlueprint`, `ContainerBlueprint`, `ModuleBlueprint`,
  `ComponentBlueprint`, `FeatureBlueprint`, `Rfc`, `Guide` — confirmed by
  grepping `schemas/frontmatter.strata` and cross-checking
  `definitions.DocumentType.enum`, which also has 11 entries). Did not
  investigate or correct the bead text's count — it's descriptive prose
  about a historical repro, not a checkable claim the fix depends on, and
  the guard's correctness was verified directly (11/11 checked, both
  reject and accept cases confirmed) rather than against that number.
- **Option 3 scope:** interpreted "a stale stamp must not be able to leave
  an older binary installed while the hook reports success" narrowly, as a
  reporting/visibility fix (turn a silent false-success message into an
  explicit `WARNING:` naming exactly why freshness is unverified) rather
  than a behavioral fix that forces a rebuild whenever fetch fails.
  Rebuilding on a failed fetch wouldn't install anything different (the
  local checkout genuinely hasn't moved), so it would only cost ~2 minutes
  for the same binary — the actual gap was that the hook's log claimed
  verified freshness ("strata CLI current") in a case where it had not
  verified anything. Fixing the message is what closes that gap; a real
  behavioral retry/backoff on fetch failure is a larger, separate change
  this bead's scope doesn't call for.

### Surprises

- `scripts/sync-strata-docs.sh --check` is red on this branch — 3 vendored
  docs (`strata-llm-reference.md`, `language-reference.md`,
  `compiler-options.md`) reported STALE — independently of anything in this
  bead. Confirmed via `git stash` (stash my two edits, rerun the check, same
  3-file failure; pop the stash back) that this predates this bead's work
  and reproduces from `f20abeb` (the `tix` commit) alone, so it's not caused
  by anything here. Filed **agent-plugins-be4** (P2, `discovered-from:
  agent-plugins-j7f`, explicitly noted as adjacent-not-blocking) rather than
  fixing it in this bead's diff, per the "stay strictly in scope" instruction.
- The assertion script needed no `additionalProperties` distinction between
  "genuinely no required fields by design" and "corrupted" — every one of
  this repo's 11 document types happens to require at least the envelope's
  `title`/`description`/`slug`/`type`/`status`/`updated_at`, so "non-empty
  required" cleanly separates good from corrupted for the whole set with no
  false positives to special-case. Worth knowing if a future document type
  is ever added with a legitimately empty `required` list — this guard
  would need widening then, not before.
